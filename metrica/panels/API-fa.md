# متریکا — APIهای لازم برای فعال‌سازی ورود، اشتراک و سهمیه‌ها

قرارداد بین فرانت‌اند (`AuthService` و `SubscriptionService` در `panels.js`) و بک‌اند. همهٔ آدرس‌ها نسبت به `METRICA_CONFIG.apiBase` هستند.

## قواعد عمومی

- فقط **HTTPS** (تنها استثنا: سرور روی همین دستگاه، `http://localhost`، برای توسعه و تست). بدنه‌ها JSON. فرانت‌اند همهٔ درخواست‌ها را با `credentials: 'include'` و هدر `X-Metrica-Client: web` می‌فرستد.
- **نشست**: کوکی `HttpOnly; Secure; SameSite=Lax` (یا `Strict`) که فقط سرور می‌سازد و می‌خواند. هیچ توکنی در بدنهٔ پاسخ برای ذخیره در مرورگر برنگردانید.
- **CORS** (اگر API روی دامنهٔ دیگری است): `Access-Control-Allow-Origin` دقیقاً برابر دامنهٔ وب‌اپ (نه `*`)، `Access-Control-Allow-Credentials: true`، `Access-Control-Allow-Headers: Content-Type, X-Metrica-Client`.
- **CSRF**: درخواست‌های POST بدون هدر `X-Metrica-Client` یا با Origin ناشناخته رد شوند.
- **خطا**: وضعیت HTTP مناسب و بدنهٔ `{ "error": "<CODE>", "retryAfter"?: <ثانیه>, "attemptsLeft"?: <عدد> }`. فرانت‌اند هدر `Retry-After` را هم می‌خواند. مهلت هر درخواست در فرانت‌اند ۱۵ ثانیه است.

| کد خطا | HTTP | پیام نمایش‌داده‌شده |
|---|---|---|
| `SERVICE_UNAVAILABLE` | 503 | سرویس پیامک / درگاه پرداخت هنوز فعال نیست |
| `INVALID_PHONE` | 400 | شماره موبایل معتبر نیست |
| `RATE_LIMITED` + `retryAfter` | 429 | «تعداد درخواست‌های کد برای این شماره به سقف مجاز رسیده است.» + شمارش معکوس «زمان مجاز بعدی» |
| `INVALID_CODE` + `attemptsLeft` | 400 | «کد واردشده صحیح نیست. لطفاً آن را بررسی و اصلاح کنید.» + تلاش باقی‌مانده |
| `CODE_LOCKED` + `resendIn` | 429 | ۵ تلاش این کد تمام شد؛ کد جدید لازم است |
| `TOO_MANY_ATTEMPTS` + `retryAfter` | 429 | «تعداد تلاش‌های شما بیش از حد مجاز است. لطفاً تا زمان اعلام‌شده صبر کنید.» + شمارش معکوس |
| `CODE_EXPIRED` | 410 | کد منقضی شده است |
| `UNAUTHORIZED` | 401 | نشست معتبر نیست |
| `SMS_FAILED` / هر خطای دیگر / 5xx | — | خطای سرور |
| قطع شبکه / مهلت | — | اتصال به سرور برقرار نشد |

`retryAfter` و `resendIn` همیشه **ثانیه از لحظهٔ پاسخ** هستند (نه ساعت مطلق)، تا اختلاف ساعت گوشی کاربر اثری نداشته باشد.

## ۱. احراز هویت با OTP

### سیاست قطعی (همه در سرور، اتمیک)

| قاعده | مقدار |
|---|---|
| طول و عمر کد | ۴ رقم (CSPRNG)، **۱۲۰ ثانیه**؛ ذخیره فقط به‌صورت HMAC |
| کد جدید | فقط بعد از تمام شدن ۱۲۰ ثانیهٔ کد فعلی (یا استفادهٔ موفق از آن)؛ کد جدید، کد قبلی را باطل می‌کند |
| درخواست کد برای هر شماره | حداکثر **۵ در هر پنجرهٔ متحرک ۱۰ دقیقه‌ای**؛ ششمی رد می‌شود (`RATE_LIMITED` + `retryAfter` تا آزاد شدن پنجره) |
| تلاش ناموفق برای هر کد | حداکثر **۵** (`CODE_LOCKED`) |
| تلاش ناموفق برای هر شماره | حداکثر **۷ در هر پنجرهٔ متحرک ۱۰ دقیقه‌ای**، روی همهٔ کدها و دستگاه‌ها؛ از تلاش هشتم، تأیید تا آزاد شدن پنجره بسته است (`TOO_MANY_ATTEMPTS` + `retryAfter`) — این بررسی **قبل از** مقایسهٔ کد انجام می‌شود و با کد جدید، بستن پنل یا رفرش دور زده نمی‌شود؛ درخواست کد جدید هم در این مدت رد می‌شود |
| ترتیب | هر محدودیتی که زودتر برسد اعمال می‌شود |
| IP و دستگاه (پیشنهادی، قابل تنظیم) | درخواست: ۲۰ برای هر IP و ۱۰ برای هر دستگاه؛ تلاش ناموفق: ۳۰ برای هر IP و ۱۵ برای هر دستگاه — همه در پنجرهٔ ۱۰ دقیقه‌ای |
| هم‌زمانی | هر «بررسی + شمارش» زیر قفل کلیدهای شماره، IP و دستگاه (به ترتیب ثابت) انجام می‌شود؛ درخواست‌های موازی نمی‌توانند از سقف عبور کنند |
| دستگاه | کوکی `mdev` (HttpOnly، تصادفی) که سرور می‌سازد؛ تأیید کد فقط از همان دستگاهی که کد را خواسته پذیرفته می‌شود |

پیاده‌سازی مرجع و آزمون‌شدهٔ همین سیاست در `server/otp-policy.mjs` است (بخش ۵).

### `GET /auth/session`
در بارگذاری صفحه صدا زده می‌شود.
- وارد شده: `200 { "user": User, "pendingOtp": null }`
- وارد نشده: `200 { "user": null, "pendingOtp": Otp | null }` — اگر همین دستگاه کدی در جریان دارد، برگردانده می‌شود تا **رفرش صفحه تایمر را ریست نکند** و قفل‌ها برقرار بمانند. (وضعیت 200 برای وارد نشده، تا کنسول مرورگر خطای 401 نشان ندهد.)

### `Otp` (پاسخ درخواست کد و `pendingOtp`)
```json
{ "requestId": "…", "phone": "09123456789", "expiresIn": 120, "resendIn": 120, "attemptsLeft": 5, "locked": false, "verifyBlockedFor": 0 }
```
- `expiresIn`: ثانیهٔ باقی‌ماندهٔ عمر کد — تایمر پنل از همین مقدار شروع می‌شود (برای کد تازه دقیقاً ۱۲۰ = «۰۲:۰۰»).
- `resendIn`: ثانیه تا مجاز شدن کد بعدی؛ هرگز کمتر از `expiresIn` نیست و اگر پنجرهٔ ۵تایی پر باشد، تا آزاد شدن آن است. دکمهٔ «ارسال مجدد کد» تا این لحظه غیرفعال می‌ماند.
- `attemptsLeft`: کمینهٔ تلاش‌های باقی‌ماندهٔ این کد و این شماره. `locked`: ۵ تلاش این کد تمام شده. `verifyBlockedFor`: ثانیهٔ باقی‌ماندهٔ قفل ۷تایی (فقط در `pendingOtp`).

### `POST /auth/otp/request`
`{ "phone": "09123456789" }` (همیشه ۱۱ رقم انگلیسی، نرمال‌شده)
- `200 Otp` — کد تازه ارسال شد.
- `200 Otp` با `"resumed": true` — همین دستگاه هنوز کد معتبری برای این شماره دارد: همان کد و همان زمان (پیامک دوباره ارسال نمی‌شود). دستگاه دیگر در این حالت `429 RATE_LIMITED` می‌گیرد.
- `429 RATE_LIMITED` / `429 TOO_MANY_ATTEMPTS` با `retryAfter`؛ `400 INVALID_PHONE`؛ `502 SMS_FAILED`؛ تا اتصال سرویس پیامک `503 SERVICE_UNAVAILABLE`.
- پاسخ برای شمارهٔ ثبت‌نشده و ثبت‌شده یکسان است (افشای عضویت نشود).
- متن پیامک: کد + خط آخر `@app.metrica.ir #1234` (دامنهٔ واقعی وب‌اپ) برای پر شدن خودکار در اندروید (WebOTP)؛ در iOS فیلد `autocomplete="one-time-code"` کافی است.

### `POST /auth/otp/verify`
`{ "requestId": "…", "code": "1234" }`
- موفق، کاربر قبلی: `200 { "user": User }` + ساخت نشست (Set-Cookie). کد پس از یک استفادهٔ موفق باطل می‌شود.
- موفق، کاربر جدید: `200 { "profileRequired": true, "user": { … } }` + نشست محدود که فقط اجازهٔ `POST /auth/profile` دارد.
- کد اشتباه: `400 { "error": "INVALID_CODE", "attemptsLeft": n }` — پنل ارقام را نگه می‌دارد، کادرها قرمز می‌شوند و همان کد رد‌شده دوباره ارسال نمی‌شود.
- `429 CODE_LOCKED` (۵ تلاش این کد) · `429 TOO_MANY_ATTEMPTS` + `retryAfter` (۷ تلاش شماره) · `410 CODE_EXPIRED` (منقضی، استفاده‌شده، جایگزین‌شده یا از دستگاه دیگر).

### `POST /auth/profile`
`{ "firstName": "…", "lastName": "…" }` (هر کدام ۱ تا ۴۰ نویسه: حروف، فاصله، نیم‌فاصله؛ سرور اعتبارسنجی کند)
- `200 { "user": User }` و ارتقای نشست به نشست کامل.

### `POST /auth/logout`
`{}` → `200 {}` و حذف کوکی نشست. (دکمهٔ «خروج از حساب» هنوز به این وصل نشده است.)

### `User`
```json
{ "id": "…", "firstName": "سارا", "lastName": "محمدی", "name": "سارا محمدی", "avatar": "https://…", "plan": "normal | plus | pro | max" }
```
فرانت‌اند `name`، `avatar` و `plan` را به `Metrica.setUser` می‌دهد.

## ۲. اشتراک و پرداخت

### پلن‌ها (منبع قطعی قیمت: سرور)
| شناسه | نام | کاربران | دسترسی | سهمیه | قیمت |
|---|---|---|---|---|---|
| `plus` | پلاس / Plus | ۱ | آنالیز ساخت | ۱ پروژه در هر ۲۴ ساعت | ۵۰۰٬۰۰۰ تومان |
| `pro` | پرو / Pro | ۱ | آنالیز ساخت، مدیریت پروژه | ۳ پروژه در هر ۲۴ ساعت | ۱٬۰۰۰٬۰۰۰ تومان |
| `max` | MAX | تا ۵ | همهٔ امکانات (آنالیز ساخت، مدیریت پروژه، کش‌فلو، مارکتینگ) | ۵ پروژه در هر ۲۴ ساعت | ۵٬۰۰۰٬۰۰۰ تومان |

دورهٔ زمانی اشتراک (ماهانه/سالانه) در داده‌های پروژه مشخص نشده و در رابط نمایش داده نمی‌شود؛ پس از تعیین، به متن پلن‌ها اضافه شود.

### `POST /subscription/checkout`
`{ "plan": "plus" | "pro" | "max" }` — فقط با نشست معتبر (وگرنه `401`).
- `200 { "paymentUrl": "https://…" }` → فرانت‌اند کاربر را به درگاه می‌برد (فقط آدرس HTTPS پذیرفته می‌شود).
- مبلغ را سرور از شناسهٔ پلن تعیین می‌کند؛ هیچ مبلغی از فرانت‌اند پذیرفته نشود.
- تا اتصال درگاه: `503 SERVICE_UNAVAILABLE`.
- بازگشت از درگاه (callback) و تأیید تراکنش (verify) فقط سمت سرور؛ پس از تأیید، اشتراک فعال و کاربر به وب‌اپ برگردانده شود. فعال‌سازی اشتراک هرگز بر اساس پارامتر آدرس بازگشت انجام نشود.
- کلیدهای درگاه فقط در سرور.

### `GET /subscription`
`200 { "plan": "max", "status": "active | expired | none", "expiresAt": "…", "seats": { "limit": 5, "used": 2 }, "quota": Quota }`

### اعضای MAX (حداکثر ۵ کاربر) — پیشنهادی
- `GET /subscription/members` · `POST /subscription/members { "phone": "09…" }` · `DELETE /subscription/members/:id`
- سقف ۵ نفر را سرور اعمال کند (`409 { "error": "SEATS_FULL" }`).

## ۳. سهمیهٔ پروژه‌ها (پنجرهٔ ۲۴ ساعته)

### `Quota`
```json
{ "limit": 3, "used": 1, "windowHours": 24, "mode": "rolling | fixed", "windowStart": "…", "resetsAt": "…" }
```
- `limit`: ۱ / ۳ / ۵ بر اساس پلن.
- `mode` در تنظیمات بک‌اند قابل تغییر است:
  - `rolling`: هر پروژه ۲۴ ساعت پس از ثبت، سهمیه را آزاد می‌کند.
  - `fixed`: پنجره از اولین استفاده (یا ساعت ثابت، مثلاً ۰۰:۰۰ تهران) شروع و ۲۴ ساعت بعد کامل تمدید می‌شود.
- در MAX سهمیه برای کل اشتراک (۵ کاربر) مشترک یا برای هر کاربر — تصمیم و پیکربندی سمت سرور.

### `GET /quota` → `200 Quota`
### ثبت پروژه / آنالیز
هر endpoint که پروژه یا آنالیز جدید می‌سازد پیش از اجرا سهمیه و اعتبار اشتراک را **سمت سرور** بررسی کند و در صورت پر بودن: `429 { "error": "QUOTA_EXCEEDED", "resetsAt": "…" }`. محدودسازی صرف در JavaScript کافی نیست.

## ۵. پیاده‌سازی مرجع سیاست OTP (برای تیم بک‌اند)

`server/` بخشی از وب‌اپ نیست؛ نمونهٔ اجرایی و آزمون‌شدهٔ همین قرارداد است:

| فایل | کار |
|---|---|
| `otp-policy.mjs` | همهٔ قواعد بالا؛ `MemoryStore` با قفل کلیدی برای اتمیک بودن در یک پروسهٔ Node |
| `api.mjs` | endpointهای `/auth/*` و `/subscription/checkout` (کوکی‌های HttpOnly، بررسی هدر CSRF، کوکی دستگاه) |
| `otp-policy.test.mjs` | ۱۴ آزمون: عمر ۱۲۰ ثانیه، جایگزینی کد، ۵ درخواست و ۷ تلاش در پنجرهٔ متحرک، ۵ تلاش هر کد، محدودیت IP/دستگاه، درخواست‌های هم‌زمان |

```bash
node --test metrica/panels/server/otp-policy.test.mjs
node metrica/panels/server/api.mjs      # http://localhost:8787/api — بدون سرویس پیامک: SERVICE_UNAVAILABLE
```

برای انتشار:
- `sms(phone, text)` را به سرویس پیامک واقعی وصل کنید (کلید فقط در سرور) و `domain` را دامنهٔ وب‌اپ بگذارید.
- با بیش از یک نمونهٔ سرور، `MemoryStore` را با ذخیره‌ساز مشترک با همان رابط جایگزین کنید: Redis (یک اسکریپت Lua برای هر «بررسی + افزودن» روی sorted set با `ZREMRANGEBYSCORE`/`ZCARD`/`ZADD`) یا SQL با `SELECT … FOR UPDATE`. محدودیت هرگز در localStorage یا JavaScript مرورگر نیست.
- کاربران و نشست‌ها را در پایگاه داده نگه دارید؛ پشت پراکسی `trustProxy` را فعال کنید تا IP واقعی خوانده شود.
- همهٔ سناریوها (صحیح، اشتباه، انقضا، ارسال مجدد، ۵ درخواست، ۷ تلاش) پیش از انتشار با `metrica/panels/tests/panels.test.cjs` روی سرور واقعی هم اجرا شوند.
